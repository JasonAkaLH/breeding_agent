## 1. 为什么拆分

原先的一期开发计划已经能表达总体方向，但对持续协作来说仍然过于集中，不利于：
- 按阶段逐步推进；
- 在某个阶段单独讨论“做什么 / 不做什么”；
- 在阶段完成后留下明确的退出条件与验收证据；
- 在一期完成后继续承接 SQLQuery LLM、主代理 Skill / LLM runtime 等增强专题。

因此，当前计划已经拆分为多份 Phase 文档，写法参考外部 `PRD/dev_processes/` 的开发文档样式。

## 3. 当前实现基线

当前仓库已经不再是“设计前最小仓库”，而是具备以下后端实现：

- `src/core/`：共享 contract、模型、枚举与错误。
- `src/storage/`：状态存储抽象与 SQLite 实现。
- `src/lifecycle/`：mailbox、interrupt/resume、cancel、conversation guard 等生命周期规则。
- `src/orchestration/`：registry、scheduler、workflow plan、router、validator、expander 与 orchestration service。
- `src/api/`：FastAPI app、routes、DTO、SSE 与 runtime 装配。
- `src/capabilities/sql_query/`：SQLQuery public macro 与内部六节点只读查询 workflow。
- `src/capabilities/main_agent/`：主代理普通回复 capability、Skill 上下文与 streaming LLM 输出。
- `src/integrations/`：LLM client、MySQL readonly adapter、audit logger、Codex Skill 兼容层。
- `configs/sql_query/`：SQLQuery 配置。
- `scripts/`：真实 LLM smoke 等显式手工脚本。
- `tests/`：按层级组织的 unittest 回归。

详细目录职责以 `README.md`、`AGENTS.md` 和 `docs/一期核心模块边界.md` 为准。

## 4. 当前已冻结的关键边界

- **Phase 4 定主代理编排标准**：它负责定义通用 orchestration 能力，并且必须兼容后续新增 capability。
- **Phase 5 适配 Phase 4 标准**：SQLQuery 只是首个 capability，它要按 Phase 4 的标准接入，而不是让 Phase 4 反向为 SQLQuery 定制。
- **SQLQuery public / internal 边界已收口**：外部只使用 `sql_query` / `sql_query.query`，内部 `sql_query.*` 节点不作为外部请求入口。
- **一期记忆边界已收口**：当前只做会话延续型记忆，不做跨任务知识沉淀；该记忆作为主框架状态存储的一部分，本地先落 SQLite，后续再迁移到 PostgreSQL。
- **真实 provider 默认不进 unittest**：SQLQuery 与主代理 LLM 均通过 fake / injected seam 走默认测试；真实 provider 只通过显式 smoke 或手工验证触发。
- **前端尚未实现**：前端 PRD 预留在 `docs/prd/frontend/`，不要把前端交互和视觉设计混入后端 PRD / Phase 文档。
