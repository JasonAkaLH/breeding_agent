## 1. 为什么拆分

原先的一期开发计划已经能表达总体方向，但对持续协作来说仍然过于集中，不利于：
- 按阶段逐步推进；
- 在某个阶段单独讨论“做什么 / 不做什么”；
- 在阶段完成后留下明确的退出条件与验收证据。

因此，当前计划正式拆分为多份 Phase 文档，写法参考外部 `PRD/dev_processes/` 的开发文档样式。

1. Phase 0：冻结一期范围与验收边界
2. Phase 1：建立核心契约与共享模型
3. Phase 2：落地 SQLite 状态存储与仓储抽象
4. Phase 3：实现生命周期与协作协议
5. Phase 4：打通编排调度与最小运行闭环
6. Phase 5：接入 SQLQuery MVP 能力链路
7. Phase 6：接入 FastAPI / SSE 对外接口
8. Phase 7：完成一期验收并评估第二阶段

## 4. 当前结论

- 计划已经不再建议继续维护为单一长文档；
- 后续讨论、修订和执行应以 `docs/dev_processes/` 为主；
- `.omx/plans/` 继续保留为运行时工作稿，不替代仓库正式文档。


## 5. 当前已冻结的关键边界

- **Phase 4 定主代理编排标准**：它负责定义通用 orchestration 能力，并且必须兼容后续新增 capability。
- **Phase 5 适配 Phase 4 标准**：SQLQuery 只是首个 capability，它要按 Phase 4 的标准接入，而不是让 Phase 4 反向为 SQLQuery 定制。
- 因此，Phase 4 的 smoke 应优先使用 mock/fake capability flow；真实 SQLQuery 业务闭环留到 Phase 5。
- **一期记忆边界已收口**：当前只做会话延续型记忆，不做跨任务知识沉淀；该记忆作为主框架状态存储的一部分，本地先落 SQLite，后续再迁移到 PostgreSQL；其实现规则是“恢复判断必需信息走独立字段，补充上下文走 JSON / refs / summary，不单独建 memory 专用表”；如后续需要，应另立长期记忆专题。
