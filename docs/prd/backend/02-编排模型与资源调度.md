# 编排模型与资源调度

> 来源：从 `docs/prd/backend/00-主代理框架PRD.md` 拆分而来，承载逻辑架构、编排模型、注册发现、资源调度与规则配置示意。

## 5. 逻辑架构
一期建议至少包含以下逻辑组件：
- **API 接入层**：接收消息、查询任务、取消任务、输出事件流。
- **会话服务**：维护 `conversation_id`、消息顺序、串行约束。
- **主代理编排器**：负责任务拆分、DAG 生成、节点策略装配。
- **Capability Registry**：维护稳定能力目录。
- **Instance Registry**：维护运行态实例、心跳、负载与健康状态。
- **调度器**：在资源约束下选择节点执行实例。
- **执行适配层**：统一封装本地执行器与外部 RESTful API。
- **状态存储**：持久化会话、任务、节点、事件、产物引用。
- **记忆服务**：维护用户账户与会话连续性记忆。
- **审计日志服务**：输出 JSONL 结构化日志。
- **事件流服务**：将任务状态和节点事件推送给前端。

### 5.1 工程代码模块划分
为降低主框架与具体 capability 实现之间的耦合，一期建议按以下模块边界组织代码：

- `core/`
  - 放稳定契约、基础类型、通用错误、状态枚举、共享模型
- `orchestration/`
  - 放主代理编排核心：任务理解、DAG 规划、完成判定、重编排入口
- `lifecycle/`
  - 放 task / node / mailbox / interrupt / checkpoint 的生命周期规则
- `storage/`
  - 放状态存储抽象接口与具体实现（SQLite、未来 PostgreSQL）
- `integrations/`
  - 放外部系统适配（LLM、MySQL 只读查询、未来生信 API）
- `api/`
  - 放 HTTP 路由、请求/响应 DTO、SSE 事件输出
- `capabilities/`
  - 按 capability 分目录组织实现，例如 `capabilities/sql_query/`

### 5.2 模块间解耦原则
模块之间应优先通过**公开契约 + 类型化数据**交流，而不是直接依赖彼此内部实现细节。

具体约束如下：
- 主框架只依赖 capability contract，不依赖 capability 内部实现
- capability 实现不直接持有主框架编排细节
- API 层不直接操作具体存储实现
- integrations 不直接理解业务 route、DAG 或 mailbox 内部规则
- lifecycle 负责状态机规则，但不直接绑定某个数据库方言

也就是说，模块之间不是“完全不调用”，而是：

> **只通过公开契约传递数据，不直接耦合对方私有实现。**

### 5.3 主框架与 capability 的上下级边界
该边界是本项目的硬约束：

> **主框架只负责任务拆解、编排、分发；capability 只负责自身能力的执行。**

这意味着：
- 主框架负责：
  - 任务理解
  - 路线选择
  - DAG 生成与修正
  - capability 选择与分发
  - 结果汇总与完成判定
- capability 负责：
  - 在自身能力边界内完成执行
  - 返回结构化结果 / 失败 / 澄清请求

主框架不得直接承担 SQLQuery、RAG、生信分析等具体业务实现逻辑；这些都应下沉到对应 capability 模块中。

### 5.4 推荐依赖方向
一期推荐保持以下依赖方向：

- `api -> orchestration`
- `orchestration -> core / lifecycle / storage interfaces / capability contracts`
- `lifecycle -> core / storage interfaces`
- `capabilities/* -> core / integrations / storage interfaces`
- `storage implementations -> storage interfaces / core`
- `integrations -> core`

明确禁止的耦合包括：
- `api -> 具体 SQLite / PostgreSQL 实现`
- `orchestration -> SQLQuery 内部 prompt / SQL guard 细节`
- `capabilities/* -> api`
- `integrations -> orchestration internals`

### 5.5 对 SQLQuery 的特别约束
SQLQuery 必须作为下层 capability 存在，而不是主框架的一部分。

因此：
- 主框架只能看到：
  - `capability_id`
  - capability 输入/输出契约
  - capability 返回的状态、结果、错误、interrupt 请求
- 主框架不能直接依赖：
  - SQL prompt 组装细节
  - schema context builder 内部规则
  - SQL guard 实现细节
  - MySQL 访问实现细节

后续新增 RAG、生信分析等 capability 时，也应遵循同样的上下级边界。

## 6. 编排模型
### 6.1 任务结构
- 一期采用**混合型 DAG**：先生成主干 DAG，执行中允许受控动态扩展。
- 支持中间结果被多个下游节点复用。
- 设计参考成熟工作流 / DAG 编排逻辑，不自造完全脱离实践的模型。

### 6.2 任务拆分指导方针
- 主代理在**预定义任务拆分指导方针**下工作。
- 拆分依据以**结构化规则**为主，prompt / 推理为辅。
- 结构化规则先由人定义业务拆分原则，后续逐步沉淀为配置。
- 主代理不可完全依赖自由 prompt 推理决定任务图。

### 6.3 子代理执行范式
- 一期采用**混合模式**：优先专用任务型 Agent，必要时允许受限 ReAct Worker。
- 受限 ReAct Worker 只可在当前 capability、节点策略、资源约束允许的范围内选择 tool。
- 不开放全局大 tool pool，不允许无边界自由扩展执行路径。

### 6.4 主代理思维模式
主代理不定义为“纯 ReAct 执行型 Agent”，而定义为：

> **受规则、状态机与完成判定约束的编排型主代理**

它的核心职责不是直接完成业务实现，而是：
- 理解用户任务
- 选择业务路线
- 生成与修正任务 DAG
- 将节点分发给 capability
- 汇总 required 路径结果
- 基于完成判定决定“收敛、澄清或继续重编排”

因此，主代理更适合采用：

> **规则约束下的分阶段审议（Stage-Gated Deliberation）**

而不是自由试错式的纯 ReAct 闭环。

### 6.5 主代理工作闭环
主代理建议采用如下闭环：

1. **理解任务**
   - 识别用户 Query、当前 route、约束条件和缺失信息

2. **编排任务**
   - 生成主干 DAG
   - 为节点绑定 capability
   - 注入 required / optional / fallback、retry、timeout、resource class 等策略

3. **分发执行**
   - 将节点交给调度器分发到可用 instance

4. **汇总与审查**
   - 汇总 required 路径的执行结果
   - 检查是否仍有关键失败、未解决 interrupt、未满足依赖

5. **决策下一步**
   - 若已满足完成条件，则收敛并输出
   - 若系统内仍可补足，则在模板允许范围内继续扩展 DAG 并重编排
   - 若缺失的是用户必要信息，则进入 interrupt / resume 流程

### 6.6 完成判定机制
主代理不依赖“感觉上已经完成”，而依赖结构化完成判定：

#### 任务级完成判定
- required 节点已完成
- 无未解决 interrupt
- 无失败的关键节点
- 当前 route 对应的结果契约已满足

#### 节点级完成判定
- 节点产物已生成
- 节点通过其 guard / verifier / completion contract
- 节点结果可被上游或最终汇总消费

#### 无法证明完成时
若主代理无法证明“当前结果已满足用户 Query”，则不得直接收敛，而应进入以下分支之一：
- **系统内可补足**：进入受控重编排
- **需要用户补充信息**：进入 interrupt / resume
- **超出能力边界或策略不允许**：终止并返回明确说明

### 6.7 重编排闭环边界
主代理允许重编排，但必须受控：
- 重编排只能在模板与策略允许范围内进行
- 不允许无限循环“再想一步”
- 应设置：
  - 最大重编排轮次
  - 最大动态扩展节点数
  - 最大澄清轮次
  - 最大资源预算

这意味着主代理的闭环不是“自由 ReAct”，而是：

> **Understand → Plan → Dispatch → Check → Conclude / Replan**

## 7. 注册、发现与资源调度
### 7.1 注册与发现
采用混合模式：
- **Capability Registry**：静态定义系统“会什么”。
- **Instance Registry**：动态反映“现在谁在线、谁可用、谁负载高”。
- 调度时先按 capability 匹配，再按实例状态和资源状态选择执行者。

### 7.2 统一执行协议
子代理统一视为“可执行实例”，一期物理部署可单机，但逻辑上统一支持：
- 本地执行逻辑
- 外部 RESTful API 适配器
- 未来远程 worker / 独立服务

### 7.3 资源调度策略
资源调度采用**混合策略**：
1. 先用硬性规则过滤可执行 Agent / 节点 / 资源。
2. 再在可行集合内基于实时负载、资源占用、能力匹配等动态评分选择。

一期资源维度至少覆盖：
- 执行并发
- Agent 能力资源
- 外部资源（模型额度、数据库连接、检索资源、CPU/内存/GPU 预算）

### 7.3.1 背压策略
一期背压策略采用：**严格拒绝型（B）**。

核心原则：
- 优先保护已经进入运行态的任务，保证已接收任务的结果质量与执行完整性。
- 不因资源不足而降级任务质量，不允许通过裁剪关键节点、跳过必需步骤或弱化执行链路来“糊弄用户”。
- 在资源池达到阈值时，不采用长队列缓冲，而是直接拒绝新任务进入。

高压下的默认动作：
- 已运行任务继续执行
- 新任务直接拒绝
- 不构造长等待队列
- 将拒绝行为写入事件流与审计日志

### 7.3.2 配额策略
一期配额策略采用：**系统级 + capability 级**。

#### 系统级配额
用于限制整个系统的总资源占用，建议至少覆盖：
- 总活跃任务数
- 总运行节点数
- 总外部 LLM 并发数
- 总 MySQL 活跃查询数
- 总外部生信 API 并发数

#### capability 级配额
用于限制单类能力对系统资源的占用上限，避免某一类 capability 吃满系统资源。建议至少覆盖：
- `sql_query.sql_generate`
- `sql_query.sql_execute_readonly`
- `sql_query.result_summarize`
- `bioinfo.external_job`

#### 触发拒绝规则
当任一关键资源池达到拒绝阈值时：
- 不再接受新的 task
- 不再调度新的高成本节点
- 返回明确的“当前繁忙，请稍后重试”结果
- 记录拒绝原因、触发资源池、触发时间与对应 capability

### 7.3.3 用户级配额预留兼容
一期暂不实现复杂的用户级配额，但必须在模型与策略接口上预留兼容：
- 不同用户等级 / 套餐可定义不同资源额度
- 不同用户等级可对应不同活跃任务上限
- 不同用户等级可定义不同 capability 可用范围或优先级权重
- 配额判定接口不应写死为“仅看系统级与 capability 级”，后续应可插入 `account_id` / `plan_id` 维度

这意味着一期虽然先不真正执行用户分层配额，但后续接入高付费用户更高额度时，不应推翻现有配额架构。

### 7.3.4 任务优先级策略
一期优先级策略采用：**来源驱动优先级**。

但优先级体系应拆成两层：

#### 第一层：控制类动作（独立最高优先级）
以下动作不进入普通任务优先级排序，而是始终按最高优先级处理：
- `cancel_notice`
- `resume_notice`
- `clarification_answer` 到达后的恢复动作
- 关键状态收敛动作
- interrupt 关闭 / 失效处理
- task context termination 传播动作

这些动作属于**控制面**，优先级独立于普通业务任务。

#### 第二层：普通任务来源优先级
普通业务任务按来源排序，当前顺序确定为：

> **resume 恢复类任务 > 用户直接发起任务 > 系统修复/重试类任务 > 普通协作型子任务**

具体含义：
- **resume 恢复类任务**：用户补充完信息后恢复原任务，优先级最高
- **用户直接发起任务**：普通对话入口新任务
- **系统修复/重试类任务**：系统内部补偿与受控重编排
- **普通协作型子任务**：依赖补全、peer context 请求、artifact 引用共享等

#### 适用边界
- 该优先级主要作用于**新进入调度器的任务 / 节点**
- 不改变“优先保护已运行中任务”的背压原则
- 不允许普通业务优先级压过控制类动作

#### 一期建议的细粒度权重
在保持“来源驱动优先级”为主的前提下，一期可补充一层**轻量权重**，但不引入复杂多因素评分系统。

建议采用如下基础权重：

| 类型 | 建议权重 |
|---|---:|
| 控制类动作 | 1000 |
| `resume` 恢复类任务 | 800 |
| 用户直接发起任务 | 600 |
| 系统修复 / 重试类任务 | 400 |
| 普通协作型子任务 | 200 |

这些权重的作用不是替代来源优先级，而是：
- 让调度器在实现上有明确排序依据
- 方便后续扩展用户级配额和更细粒度权重
- 避免只靠文本优先级描述，无法落地排序逻辑

#### 同来源内的二级排序因子
在相同来源类别内部，一期建议只引入少量、可解释的二级排序因子：
- `required` 路径节点高于 `optional` / `fallback`
- 已接近完成的恢复任务高于刚进入恢复的任务
- deadline 更近的任务高于 deadline 更远的任务
- 创建时间更早的任务高于更晚进入的同类任务

也就是说，一期优先级策略是：

> **来源类别决定大顺序，少量结构化因子决定同类内顺序。**

#### 一期不前置的权重维度
以下权重维度不作为一期正式调度依据，但必须预留兼容：
- 用户套餐等级权重
- capability 成本系数权重
- 业务收益 / 商业价值权重
- 历史失败率或成功率权重
- mailbox 消息密度或协作复杂度权重

这些因子后续若接入，应作为来源优先级之上的补充，而不是推翻当前两层模型。

## 13. 结构化规则配置示意
一期不强制先实现完整 DSL，但建议预留如下配置形态：

```yaml
routing_rules:
  - when:
      intent: document_retrieval
    then:
      root_capability: document.retrieve

  - when:
      intent: mysql_query
    then:
      root_capability: mysql.sql_query_query

node_templates:
  bioinfo.external_job:
    criticality: required
    dependency_type: hard
    retry_policy:
      max_attempts: 1
    timeout_policy:
      execution_seconds: 1800
    resource_class: external_api
```
