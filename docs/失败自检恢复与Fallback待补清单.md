# 失败自检、恢复与 Fallback 待补清单

更新时间：2026-05-24

本文档记录基于当前代码静态扫描得到的待补项。范围只覆盖失败自检、恢复、降级与 fallback 可靠性；不改变现有 fail-closed 安全边界，不把安全拦截、权限拒绝、SQL 写入拦截、Rust enforce 缺失等安全失败伪装成成功。

## 优先级 P0：后端执行恢复闭环

### 1. 节点级异常应进入节点失败与重规划链路

**现状**：节点执行过程中如果发生调度器找不到可用实例、执行器抛出异常、运行时边界异常等非业务返回错误，外层会把整个任务标记为执行崩溃。

**问题**：这类失败绕过了节点失败、完成策略和重规划机制，导致本来可以由 replan 或 fallback 节点接管的场景直接变成整个任务失败。

**待补目标**：
- 节点执行边界捕获可归属到当前节点的异常。
- 保存节点失败状态，并发出节点失败事件。
- 让完成策略按既有规则判断是否可重规划。
- 仅对无法归属、存储严重损坏、状态不可读取等系统级异常保留任务级 crash。

**验收口径**：模拟无可用实例、能力执行抛异常、能力返回 retriable 错误三类场景，任务均能留下节点失败证据；有 replan 预算时进入重规划，无预算时任务失败。

### 2. 节点 retry_policy 与 timeout_policy 需要实际执行

**现状**：节点计划和持久化模型中已有 retry / timeout 字段，但执行链路主要依赖各局部 adapter 自己重试；系统级节点重试与超时 envelope 不完整。

**问题**：能力返回的 retriable 标记、MCP transient、数据库 transient、sidecar transient 不能稳定转化为统一重试行为。

**待补目标**：
- 为每个节点执行建立统一超时边界。
- 对 retriable 错误按节点策略做有上限重试。
- 每次尝试记录 attempt、原因和最终结果。
- 取消中的任务不得继续重试。

**验收口径**：构造一次 transient 后成功、持续 transient 到上限、执行超时、取消中停止重试四类测试。

## 优先级 P1：用户可见恢复体验

### 3. SSE 事件流应支持自动重连并利用后端 replay

**现状**：后端已经支持事件 replay 和事件去重基础；前端 fetch 事件流失败后只查询一次任务状态，不会自动重新订阅。

**问题**：网络短断时，任务可能继续执行，但前端停留在旧状态，用户需要刷新或重新进入会话才能恢复。

**待补目标**：
- 前端事件流断开后按指数退避重连。
- 重连使用同一个任务事件接口，由后端 replay 补齐断线期间事件。
- 继续沿用事件 ID 去重，避免重复增量污染回答。
- 终态任务停止重连。

**验收口径**：模拟事件流中断后任务继续输出，前端能自动恢复并展示完整最终结果；重复事件不会重复渲染。

### 4. 结果 artifact 加载失败后应保留重试入口

**现状**：任务完成后如果结果 artifact 加载失败，前端会把任务标记为完成并提示稍后重试，但当前气泡缺少明确重试动作和任务关联恢复。

**问题**：后端任务实际成功，但用户看不到结果，且没有低成本恢复路径。

**待补目标**：
- 保留失败任务的 task id 与 assistant 气泡关系。
- 在气泡中显示“重新加载结果”入口。
- 历史消息刷新失败与 artifact 拉取失败分别提示。

**验收口径**：模拟 artifact API 首次失败、二次成功，用户可在不重发任务的情况下恢复结果展示。

### 5. 上传文件缺失不能静默降级

**现状**：消息提交时会收集缺失的 upload id，但后续只注入成功解析的文件，缺失项没有前端提示或后端 fail-early。

**问题**：用户以为文件已随消息提交，实际任务没有文件；文件类 Skill 可能后续才报缺输入，主代理也可能在无文件上下文下回答。

**待补目标**：
- 对缺失 upload id 产生明确前端提示或请求失败。
- 对强依赖文件的显式 Skill，在任务创建前 fail early。
- 对非强依赖场景，可继续执行但必须在 metadata / 事件中记录缺失事实。

**验收口径**：提交不存在、已删除、跨账号 upload id 时，用户能看到明确提示，后端不会静默忽略。

## 优先级 P1：审计与旁路可靠性

### 6. 事件发布中的审计写入失败不能阻断 SSE 投递

**现状**：事件发布时先写审计 sink，再投递给订阅队列；该审计写入未隔离异常。

**问题**：审计后端短暂失败可能影响用户可见事件流，与其他 shadow / safety 审计“失败不影响用户结果”的口径不一致。

**待补目标**：
- 事件审计写入失败降级为内部诊断，不阻断事件入队。
- 保留审计失败计数或轻量 warning，便于运维发现。
- 不吞掉事件持久化失败；持久化失败仍应被视为核心错误。

**验收口径**：模拟审计 sink 抛异常，SSE 订阅者仍收到事件，任务执行不受影响。

### 7. Runtime sidecar enforce 写路径应接入 bounded retry

**现状**：sidecar contract 已定义可重试 typed error、幂等键和 bounded retry plan；部分 enforce 写路径直接调用 sidecar 并消费响应。

**问题**：短暂 sidecar transient error 可能立即导致失败，未利用已定义的幂等重试能力。

**待补目标**：
- 将 enforce 写操作包装到统一 sidecar retry helper。
- 只有满足幂等键、同一 sidecar、错误码可重试、次数未超限时才重试。
- 每次 retry 记录脱敏审计。

**验收口径**：构造第一次 sidecar transient、第二次成功，用户可见操作成功；无幂等键或不可重试错误仍 fail closed。

## 优先级 P2：可用性策略确认

### 8. Planner provider 失败是否降级到主代理，需要产品策略确认

**现状**：当 planner 启用时，planner provider / network failure 明确不转 deterministic routing，而是规划失败。

**取舍**：这是偏安全和可审计的 fail-closed 设计；但从可用性看，planner LLM 短暂不可用时可以降级为主代理单节点回答。

**待补目标**：
- 明确产品策略：planner provider failure 是否允许降级。
- 如果允许，必须在任务 metadata 和审计事件中标记 planner fallback reason。
- 如果不允许，应在文档中明确这是安全决策，不作为缺陷。

**验收口径**：无论选择哪种策略，都要有回归测试证明 planner 输出非法、planner provider 失败、planner disabled 三种状态的行为不同且可审计。

### 9. 主代理 LLM provider 失败是否需要多 provider / 模板化降级

**现状**：主代理 LLM 失败会转为结构化 retriable 错误和审计事件，不会给用户生成备用回答。

**取舍**：没有备用 provider 时，凭空生成模板回答可能误导用户；但可以提供更友好的失败文案、稍后重试入口或备用 provider 链。

**待补目标**：
- 明确是否支持 provider failover。
- 如果不做 failover，前端应展示可重试提示，而不是泛化失败。
- 如果做 failover，需要保留 provider 切换审计、超时上限和成本边界。

**验收口径**：模拟主 provider 失败，用户看到明确可重试提示；如配置备用 provider，则最终回答标明 fallback 来源并留审计。

## 不应补成 fallback 的边界

以下场景应继续 fail closed，不应降级成成功：

- SQL 写入、越权表访问、系统库访问、多语句等安全拦截。
- 账号权限不匹配、跨账号上传文件、会话归属不一致。
- Rust / safety / MCP enforce 模式下缺少受信 artifact、contract mismatch 或必需 sidecar 不可用。
- Skill 或 MCP 配置声明为 required 且不可用。
- 结果无法通过 schema / contract 校验且没有安全 deterministic fallback。

## 建议落地顺序

1. 节点异常归一化为节点失败，并接入重规划。
2. 节点 retry / timeout envelope。
3. 前端 SSE 自动重连与 artifact 重试入口。
4. 审计 sink 失败隔离。
5. 上传缺失提示 / fail early。
6. Runtime sidecar bounded retry。
7. Planner / 主代理 provider fallback 策略确认与实现。
