# 一期核心模块边界

## 目的

本文件用于把一期主框架的模块职责和依赖方向写成仓库内的正式约定，供 Phase 2 ~ Phase 6 直接引用，而不是靠口头约定理解。

## 模块职责

### `src/core/`
- 承载稳定契约、共享模型、状态枚举、基础错误、跨模块 port。
- 只表达跨 capability 共享语义，不承载具体 capability 业务细节。

### `src/storage/`
- 承载状态存储抽象与实现。
- 面向 `core` 暴露的共享模型和 contract 实现 SQLite / PostgreSQL 等存储能力。

### `src/lifecycle/`
- 承载 task / node / mailbox / interrupt / checkpoint 的生命周期规则。
- 不直接绑定具体数据库方言。

### `src/orchestration/`
- 承载任务理解、DAG 规划、完成判定、重编排入口、registry / scheduler 等主框架编排职责。
- 只消费 capability 级 contract，不直接理解 capability 内部业务实现。

### `src/api/`
- 承载 HTTP 路由、请求/响应 DTO、SSE 事件输出。
- 不直接依赖具体存储实现。

### `src/integrations/`
- 承载外部系统适配，如 LLM、MySQL 只读访问、未来外部服务接入。
- 不直接理解 orchestration 内部规则。

### `src/capabilities/`
- 按 capability 分目录组织具体能力实现。
- 每个 capability 只负责自身业务执行，不回灌主框架内核。

## 允许依赖方向

- `api -> orchestration`
- `orchestration -> core / lifecycle / storage interfaces / capability contracts`
- `lifecycle -> core / storage interfaces`
- `capabilities/* -> core / integrations / storage interfaces`
- `storage implementations -> storage interfaces / core`
- `integrations -> core`

## 禁止依赖方向

- `api -> 具体 SQLite / PostgreSQL 实现`
- `orchestration -> capability 内部业务细节`
- `capabilities/* -> api`
- `integrations -> orchestration internals`

## 一期对共享层的特别要求

1. `src/core/` 必须面向**未来可新增 capability** 保持通用承载能力。
2. 这种通用性只体现在 capability-generic 的模型、状态、artifact、event、interrupt、contract 语义上。
3. `src/core/` 不允许出现 NL2SQL 专名或其他 capability 专名。
4. 不为了未来 RAG / 数据分析 / 生信分析等能力提前定义专用模型或复杂抽象层。

## 对现有 `src/nl2sql/` 的处理

- Phase 1 保持 `src/nl2sql/` 原位，不在本阶段迁移。
- Phase 1 只要求未来 `src/nl2sql/` 能消费 `src/core/` 的共享语义。
- 若后续需要迁到 `src/capabilities/nl2sql/`，应在 Phase 5 统一处理。

## 当前阶段的边界控制

- Phase 1 只建立 `src/core/` 与 `tests/core/`。
- 不通过创建空目录/空包的方式提前铺 `src/storage/`、`src/api/`、`src/orchestration/`、`src/capabilities/` 等后续阶段骨架。
