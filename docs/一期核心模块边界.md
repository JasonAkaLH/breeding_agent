# 一期核心模块边界

## 目的

本文件用于把当前后端主框架的模块职责和依赖方向写成仓库内的正式约定，供后续维护、二期增强和前端对接时引用，而不是靠口头约定理解。

> 当前状态：Phase 0~7 一期闭环已完成，Phase 5.5 / 8 / 8.1 / 8.2 已继续补齐 SQLQuery LLM 增强、主代理 Skill 兼容层、SQLQuery 宏能力边界与主代理真实 LLM runtime 绑定。因此本文件描述的是当前实现基线，而不是 Phase 1 的空白骨架阶段。

## 当前代码目录职责

### `src/core/`
- 承载稳定契约、共享模型、状态枚举、基础错误、跨模块 port。
- 只表达跨 capability 共享语义，不承载具体 capability 业务细节。

### `src/storage/`
- 承载状态存储抽象与实现。
- 当前已有 SQLite 实现；后续 PostgreSQL 应保持逻辑模型同构并通过适配层迁移。

### `src/lifecycle/`
- 承载 task / node / mailbox / interrupt / checkpoint / cancellation / conversation serial guard 的生命周期规则。
- 不直接绑定具体数据库方言。

### `src/orchestration/`
- 承载 capability registry、instance registry、scheduler、workflow/task plan、completion policy、backpressure、workflow router、planner contract、plan validator、macro expander 与 orchestration service。
- 只消费 capability 级 contract，不直接理解 capability 内部 prompt、SQL Guard 或外部 provider 细节。

### `src/api/`
- 承载 FastAPI app、HTTP routes、请求/响应 DTO、SSE 事件输出与 runtime 装配。
- 不直接依赖具体 SQLite / PostgreSQL repository 实现；通过 runtime 与 storage façade 装配。

### `src/integrations/`
- 承载外部系统适配，如 LLM client、MySQL readonly adapter、audit logger、Codex Skill 兼容层。
- 不直接理解 orchestration 内部规则；只提供被 capability / runtime 调用的适配能力。

### `src/capabilities/main_agent/`
- 承载 `main_agent.respond` 主代理 capability。
- 负责 Skill 匹配结果、上传 artifact metadata、受控脚本输出与用户消息的 prompt 组装，并通过 streaming LLM seam 产生主代理回复事件。

### `src/capabilities/sql_query/`
- 承载 SQLQuery public macro 与内部六节点只读查询 workflow：intent route、schema context、SQL generate、SQL guard、readonly execute、result summarize。
- 外部只应看到 `sql_query.query` / `sql_query`，内部 `sql_query.*` 节点不得作为外部请求入口。

### `src/sql_query/`
- 保留 SQLQuery 领域模型与 schema context builder 等可复用资产。
- 当前不是独立 capability 入口，而是被 `src/capabilities/sql_query/` 复用。

### `configs/sql_query/`
- 承载 SQLQuery routing rules、schema metadata、SQL Guard rules。
- 修改这些配置会影响 SQLQuery prompt、字段裁剪、SQL Guard 与真实库查询行为，必须配套测试或 smoke 说明。

### `scripts/`
- 承载显式手工 smoke / 维护脚本。
- 当前 `scripts/smoke_main_agent_llm.py` 会访问本地 `config.yaml` 配置的真实 LLM provider，不属于默认 unittest 回归。

## 文档目录职责

### `docs/prd/`
- PRD 总目录。
- 后端 PRD 统一放在 `docs/prd/backend/`。
- 前端 PRD 后续放在 `docs/prd/frontend/`，不要混入后端 PRD 总览。

### `docs/dev_processes/`
- 开发流程文档总目录，按领域拆分。
- 后端 Phase 0~8.2 文档放在 `docs/dev_processes/backend/`。
- Phase 文档是实施过程记录，不替代 PRD。

### `docs/` 其他文件
- 承载 LLM 接入建议、SQLQuery prompt 模板、一期验收报告、架构图、状态流转图与阶段性说明。
- 历史阶段文档可以保留当时语境，但若作为当前入口引用，应同步标明当前实现基线。

## 允许依赖方向

- `api -> orchestration / lifecycle / storage interfaces / integrations for runtime wiring`
- `orchestration -> core / lifecycle / storage interfaces / capability contracts`
- `lifecycle -> core / storage interfaces`
- `capabilities/* -> core / integrations / storage interfaces / capability-local helpers`
- `storage implementations -> storage interfaces / core`
- `integrations -> core`（必要时可依赖第三方 SDK / driver，但不依赖 orchestration internals）
- `src/capabilities/sql_query -> src/sql_query`（复用 schema context builder / 领域模型）

## 禁止依赖方向

- `api -> 具体 SQLite / PostgreSQL repository 细节`
- `orchestration -> capability 内部业务细节`
- `orchestration -> SQLQuery prompt / SQL Guard / MySQL adapter 细节`
- `capabilities/* -> api`
- `integrations -> orchestration internals`
- `core -> capabilities/*`
- `core -> SQLQuery / main_agent 专名或其他 capability 专名`

## 当前边界控制

1. `src/core/` 必须继续面向未来可新增 capability 保持通用承载能力。
2. 通用性只体现在 capability-generic 的模型、状态、artifact、event、interrupt、contract 语义上。
3. 不为了未来 RAG / 数据分析 / 生信分析等能力提前定义专用模型或复杂抽象层。
4. 新增 capability 时，应优先放入 `src/capabilities/<capability_name>/`，并配套 `tests/capabilities/<capability_name>/`。
5. 新增外部系统适配时，应优先放入 `src/integrations/`，capability 只依赖最小接口或 adapter。
6. 不新增空目录、空测试或占位实现；目录出现应对应明确代码、配置、文档或测试职责。
