# 旧前端 API 兼容层实现计划

状态：`planned_not_implemented`。本次交付仅为实现计划，不代表兼容服务已经实现、测试或部署。

## 1. 已确认目标与基线

- 旧版本：`1e48266b9e874f95be8087032c0dbf8018363377`，对应用户指定的 7 月 2 日无环境后缀 `0.1.23` 前后端。
- 新版本审计基线：`main@88726f7a2aa5a9d9ed576ca71aecc84cb8e554b2`。实际接入哪个后端部署，由部署配置指定；不能把本地 main 等同于生产服务器正在运行的版本。
- 新前端保留全部功能，继续连接新版后端原入口。
- 旧前端通过独立兼容层使用原有业务流程；新增 MCP 设置、凭据和授权管理使用新前端入口。
- 兼容层对外端口固定为 **51998**。允许调整旧前端 API 目标地址或旧入口转发配置。
- 新前端、新后端、Runtime Sidecar 的业务代码、镜像和现有部署不随兼容层修改；不修改数据库结构和业务数据。
- 当前工作分支是 main。本计划不切换分支，不操作生产，也不读取或改写 `docker_cmd/` 受保护文件。

成功标准是：固定旧前端的原有业务功能逐项通过兼容入口验收，新前端仍通过原入口完成原有和新增功能。接口返回 202 只是请求提交成功，不能作为功能兼容完成的证据。

## 2. 架构与交付边界

```text
旧前端 ── API 请求 ──> 服务器:51998 ── 独立兼容服务 ──> 新版后端
新前端 ── 原有入口 ────────────────────────────────> 新版后端
```

采用独立 HTTP 服务。后端内置中间件需要修改新版后端，浏览器脚本适配需要改变旧前端运行行为，均不作为本计划实施路线。独立服务增加一份部署，但转换规则、故障范围和回滚入口清晰。

### 2.1 对外接口与网络

1. HTTP 直接接入时宿主机映射 `51998:8000`，容器内应用监听 8000。若独立 TLS 入口占用宿主机 51998，应用只在内部网络暴露 8000，避免两个容器重复绑定宿主机端口。
2. 同时接受 `/api/v1/*` 和 `/seedpilot/api/v1/*`，后者只去掉一个精确 `/seedpilot` 前缀；统一请求上游 `/api/v1/*`。
3. 首期只开放旧前端需要的 HTTP 方法与路径，以及兼容服务自己的 `GET /healthz`。新增 MCP 设置接口继续走新版入口。
4. `51998` 是兼容 API 端口，不自动提供旧前端静态页面。能配置 API 地址的旧客户端直接连接；原版旧镜像使用构建时配置的同源 `/seedpilot`，需在旧入口将 API 流量转发到兼容服务。
5. 浏览器直接跨端口访问时，由兼容服务处理明确 Origin 白名单的 CORS/OPTIONS，并允许 Authorization 等所需请求头、暴露下载所需响应头。不得要求修改新版后端 CORS。
6. 旧页面为 HTTPS 时，兼容入口也必须使用浏览器可接受的 HTTPS 接入；修改端口不能解决 mixed-content 问题。TLS 使用部署环境的入口能力，端口仍为 51998。
7. 上游地址由运营者配置，客户端不能通过 URL、请求头或请求体选择任意上游。上游 URL 不得指回兼容入口形成循环。

### 2.2 运行参数

| 参数 | 用途与规则 |
|---|---|
| `LEGACY_UPSTREAM_BASE_URL` | 必填，新版后端可达的固定 origin，不包含 `/api/v1`；不写入凭据，不默认猜测开发或生产地址。 |
| `LEGACY_ALLOWED_ORIGINS` | 浏览器跨域接入时配置准确 origin，包括协议和端口；未配置只支持同源接入。 |
| `LEGACY_NEW_FRONTEND_URL` | 配置新前端页面入口，供复杂 MCP 交互引导使用；不虚构当前前端不存在的 Task 深链。 |
| `LEGACY_MODEL_EFFORT_MAP_FILE` | 按目标模型目录生成并审阅的显式强度映射；映射规则固定在一次兼容服务发布内。 |

宿主机、上游地址、旧页面 Origin、新页面入口和可用模型清单是未来部署时的环境输入。本计划不填入推测的生产地址或凭据，也不需要为编写计划取得这些访问权限。

### 2.3 独立性与状态

- 使用 Python、FastAPI、httpx、uvicorn，版本优先沿用仓库现有锁定版本；兼容服务仅安装自身需要的依赖。
- 通过公开 HTTP API 访问新版后端，不导入 `src/api/runtime.py`，不直接连接数据库、Sidecar、模型服务或 MCP Server。
- 首期不增加数据库、Redis、后台任务队列或第二套任务状态机。转换状态限于当前请求/SSE 连接；重连从上游公开 Task、Interrupt、Artifact、History 恢复。
- 用户、会话、任务、附件、授权和消息身份以新版后端为准。兼容服务不签发替代 token，不保存 MCP 凭据，不为越权资源补读存储。
- 默认不自动重试有副作用的 HTTP 请求，不把上游尚未确认的消息或授权答复提前伪造为 202。

## 3. 必须实现的转换合同

### 3.1 请求、能力与模型

| 输入或场景 | 兼容规则 | 验收要点 |
|---|---|---|
| 旧 `main_agent.respond`，没有 Skill 绑定 | 转为 `routing_mode=auto`、`capability_id=null`；保留正文、会话、附件和消息 ID。 | 普通聊天完成，旧 capability 不进入新后端。 |
| 旧 `main_agent.respond` + `metadata.soft_skill_binding.capability_id` | 验证 Skill 当前可见且可用，转为 `hint + skill.*`；只删除已完成转换的旧绑定元数据。 | 任务确实携带所选 Skill hint，不只是避免报错。 |
| 已清空旧主 Agent ID，但仍携带 `soft_skill_binding` | 同样提取真实 Skill，生成 `hint + skill.*`；若与已有顶层 Skill 选择冲突则拒绝。 | 兼容局部修改过的旧请求，不静默丢弃 Skill 选择。 |
| `auto` 携带非空 capability | 对固定旧客户端已证明的语义做规范化；其他未知/矛盾输入保持错误，不一律清空 capability。 | 不丢失用户明确的能力选择，不把未知 ID 变成普通聊天。 |
| 已经是合法新版请求形状 | 保留语义，不做二次降级。 | 相同规范化输入产生相同上游请求。 |
| 模型目录、缓存模型 ID | 返回旧前端可读的 value/label，并以新版可用目录为准；模型失效时要求重新选择。 | 不将未知模型悄悄替换为默认模型。 |
| `minimal/high/max` 与 thinking 开关 | 同名且合法的参数原样使用；不支持的强度只按显式模型映射转换。thinking 状态必须保持，不把关闭改成开启。 | 每个发布模型都覆盖旧 UI 的开关与强度组合。 |
| 不支持旧 UI 全部 thinking 开关组合的模型 | 不作为旧入口的可选模型；新入口仍正常提供。旧缓存提交返回真实参数错误。 | 目录中至少存在能满足旧 UI 控件组合的模型，否则旧入口不能宣称可用。 |
| 同一 `client_message_id` 重试 | 保留原 ID，规范化规则在该兼容版本内确定；冲突继续返回错误。 | 相同请求重试不重复执行，不同正文不能覆盖旧消息。 |
| 上传与文件选择 | 保留 multipart、upload_ids 和旧客户端实际发送的有效补参字段。 | 上传正文不转成 JSON/Base64，不无故重传附件。 |

模型强度转换是发布配置的一部分：实施时先枚举目标目录，为缺少同名强度的组合给出明确映射表和差异说明，再启用该模型。不得用随模型目录变化的“自动取最高/默认值”改变一次重试的请求内容。

此前审计发现的自定义客户端 `file_intent`、`accepted_file_types` 等历史别名，不是固定旧前端的常规请求。首期不实现任意历史客户端兼容；若真实旧前端 fixture 证明需要，再逐字段加入映射和测试。

### 3.2 HTTP 响应、最终回答与业务产物

1. 保留旧接口已有字段与类型。新增字段是否保留由实际旧 parser 测试确定，不能把“新增字段”一概当成不兼容。
2. Task、Conversation、Message、Upload 的真实 ID 保持不变，便于两个前端查看同一份数据。
3. 最终答案只使用新版正式 final Artifact 或该 Task 对应的正式 assistant history；不能取第一个 text 作为答案。
4. 旧 parser 使用 `main_agent.respond` producer 或 `main_agent_response/main_agent_text` ID 识别答案。优先只投影最终 text 的展示 producer，并保持 Artifact ID、下载身份不变；若旧界面因此产生节点关联问题，再以测试证明是否需要一致的展示节点映射。该转换绝不回写上游。
5. 文件下载经兼容入口转发，保留文件名、类型、状态码和真实下载鉴权。只改写已知上游或相对下载 URL，禁止从任意远端 URL 拉取内容。
6. 原有 Skill 的查询表格、OCR 文本、生成文件分别使用旧 parser 对照测试；不能用普通回答存在代替这些卡片的验收。
7. 新 `mcp_result` 只读取公开 `mcp_business_result` 及投影状态。可确定语义的内容转换成旧支持的表格/文本视图；通用安全摘要可附加到兼容响应中的最终文本，并明确标注来源，不持久化到新后端。
8. 无法确定内容语义时展示安全摘要和新入口提示。deferred、永久不可用、执行状态未知必须保留其含义，不伪装为成功空结果，不尝试读取或开放 raw MCP result。
9. 当前结果与刷新后的历史使用同一套展示规则，防止实时正确、刷新后又缺失或错选答案。
10. graph 返回真实活动节点与空 edges；不生成虚假的 DAG 依赖关系、关键路径或调度结论。

### 3.3 SSE 事件与恢复

兼容 SSE 是独立的事件消费与投影模块，不能用字符串全局替换实现。

| 新版事实 | 旧入口输出 |
|---|---|
| `agent.run.completed` | 旧 `task.completed`；必要时先发送真实最终文本的 `main_agent.output_delta/output_final`。 |
| `agent.run.failed` | 旧 `task.failed`，保留失败状态和可公开错误信息。 |
| `agent.run.cancelled` | 旧 `task.cancelled`，不得改成完成。 |
| `agent.run.waiting` | 先确认当前 open Interrupt，再生成旧 `node.waiting_for_input` 和一致的 interrupt_id/node_id。 |
| `agent.run.resumed` | 使用旧客户端可识别的恢复事件；只针对当前 Task 和真实恢复。 |
| 已兼容的 Skill/节点进度 | 保留必要字段，验证旧 reducer 的活动卡片更新。 |
| `auth.invalidated` | 保持登录失效语义，终止流与上游订阅。 |

实现约束：

- 同时生成正确的 SSE named event 和 JSON envelope.event_type，保持 task_id、conversation_id、node_id 等关联一致。
- 衍生 event_id 由上游事件身份和转换种类确定，同一事件重新投影不能生成全新随机 ID。
- 当前上游 SSE 路由没有暴露可直接使用的 Last-Event-ID 恢复合同；不能假设把该请求头转发就完成断点续传。
- 对历史事件回放、重复终态、已回答的 Interrupt 和新连接快照分别处理。新连接不能因回放旧 waiting 事件重新弹出已结束的补参问题。
- 使用完整 SSE 帧解析，处理跨 chunk UTF-8、多行 data、CRLF、心跳、断连和慢消费者；有界缓冲并保留背压，不一次性读完整个流。
- 上游完成与结果展示分开判断：最终结果尚不可读时，不生成虚构文本；通过公开只读接口做有界补查。若仍不可读，保留真实任务终态并提供结果暂不可用提示，不把已完成任务改成执行失败。
- 上游没有最终文本逐 token 公共流时，可在结果可读后发送一次完整 delta，再发终态；不得人为切片冒充实时模型输出。
- `agent.reasoning_delta/reset` 具有样本撤回语义，旧 UI 只会追加。首期不实时转发可撤回 reasoning，改用真实活动状态；只有公开合同能证明内容已稳定时才考虑补充展示。不得读取内部审计流或把瞬时 reasoning 存库重放。
- 下游断开时关闭对应上游 SSE；退出、token 失效、服务重启不能留下无限后台订阅。

### 3.4 Interrupt、MCP 授权与在线状态

普通 Skill 文本补参、附件补交和工作表选择属于旧功能，必须验收完整闭环。

MCP 设置留在新入口，但旧对话仍可能调用用户已配置的 MCP，因此兼容层必须处理运行中的等待状态：

1. GET Interrupt 时，按真实 reason_code 构造旧界面能显示的问题说明；保留真实 interrupt_id。
2. 简单 Tool 授权使用明确输入：`仅本次允许` → `allow_once`，`始终允许此工具` → `always_allow`，`拒绝` → `deny`。展示工具与授权范围，不把普通“好/继续”推断为授权。
3. 答复前用当前用户身份重新读取该 Interrupt，校验归属、状态与类型，生成 `metadata.mcp_tool_approval`；已原生携带结构化答复的请求不得重复转换。
4. 简单 MCP 单字段输入按公开 schema 转成 `mcp_input_responses`；类型、枚举、多字段或额外确认无法由旧 UI 明确表达时，在问题中引导进入新前端同一会话处理。
5. 用户主动取消 Task 时转发真实取消接口；不能把授权拒绝、关闭页面和取消远端任务混为一谈。
6. 保留同步补参 POST 的真实结果，不提前返回假成功。仅在真实用户补参请求存续期间，允许为同一 owner/task 建立受限上游订阅以承接等待/完成与在线状态；请求结束或断开即释放，后续 SSE 重新读取当前状态。
7. 原版旧前端在显示 Interrupt 后关闭 SSE，新后端 MCP 在线服务默认离线宽限为 300 秒。这是实际语义边界：适配器不能在用户离开后无限保活，也不能假装取消没有发生。
8. 必须测试连续两次授权、同步 POST 期间再次等待、超出实际离线宽限、切换新入口后返回旧入口。若仅靠公开接口无法通过，记录为发布阻断或明确的新功能交接限制，不能宣称全量无损兼容。

### 3.5 鉴权、错误与资源隔离

- 登录、刷新、退出使用新版公共接口；Bearer token 透传。旧 token 失效时重新登录，不从失效 token 推导可信身份。
- 所有 Task、Artifact、Interrupt 的补查也必须使用请求者的 token；不能使用共享管理员 token。
- 401/403、真正的会话忙、消息身份冲突、参数错误、资源缺失和上游不可用保留真实含义；响应正文保留可追踪错误码。
- 旧前端的错误文案按 HTTP status 写死，忽略服务端 detail。仅改 JSON 不能使其显示任意新文案；非 busy 的 409 可在明确映射表中转为旧参数错误类别，同时在正文保留原状态/错误码，不能将错误改成 200。
- 本地校验失败与上游已经受理后连接中断分别记录；后者不能自动重新提交并创建第二个任务。
- 只记录路由、状态、耗时和错误类别等低敏诊断，不记录 Authorization、正文、上传内容或 MCP 凭据。

## 5. 实施顺序与每阶段完成条件

### P0：固定合同与功能清单

- 从两个固定提交提取公开 HTTP 合同、旧 TS 请求生成器、SSE parser/reducer、Artifact parser 和 Interrupt 组件行为。
- 用独立临时 archive/build 运行旧客户端，保留来源提交与脱敏 fixture；不切换当前工作树，不引入旧依赖到新版前端。
- 将旧版 22 个公开 HTTP 操作逐项标记为透传、请求转换、响应转换或 SSE 转换，确认端口前缀覆盖完整。
- 固定原有业务场景：登录、会话列表/重命名/删除、历史、普通聊天、Skill 选择、模型/思考开关、文件上传/列表/删除、补参、取消、结果展示/下载、刷新重连。
- 按目标可用模型与 Skill 列出能力依赖；缺失业务实现不能算协议兼容器缺一条映射就可解决。
- 先建立已知失败样例：`main_agent.respond`、Skill hint 丢失、新终态不识别、多 text 误选、连续授权。

完成条件：旧客户端直接调用新版时的预期失败被稳定复现；每个旧功能有对应测试场景，发布所需环境输入有清晰清单。

### P1：独立服务与透明代理

- 新建独立应用、HTTP client 生命周期、配置校验、路径别名、方法/路径白名单、healthz 和 CORS。
- 打通登录、会话、文件上传/下载的透明转发；移除逐跳头，改写正文后重新计算长度/编码相关响应头。
- 大文件、SSE 和普通 JSON 使用不同的读取路径；上传/下载保持有界内存与连接清理。

### P2：消息准入与 Skill/模型转换
