# 第二阶段评估输入

> 日期：2026-04-23  
> 前提：一期验收已通过，当前文档只提供二期立项输入，不包含实现承诺

## 1. 总结论

**建议：可以启动“第二阶段专题规划”，但不建议把所有候选主题合并成一个大阶段同时开工。**

推荐采用“专题拆分、逐个立项”的方式推进，而不是把 PostgreSQL、长期记忆、第二 capability、LLM 化一次性打包。

## 2. 候选主题分层

### 2.1 优先级 A：最接近现状的工程化增强

#### 主题 A1：SQLite → PostgreSQL 正式化
- 目标：把当前本地同构状态存储迁移为正式数据库方案
- 触发条件：
  - 需要更稳定的持久化与并发访问
  - 需要跨进程 / 多实例运行前置条件
- 前提：
  - 复核现有 SQLite → PostgreSQL 修改清单
  - 明确迁移策略、索引策略、回归策略
- 现在不做的原因：
  - 一期验收目标已满足
  - 当前本地 SQLite 足够支撑一期闭环与验收

#### 主题 A2：公开 interrupt / resume 产品面
- 目标：把当前 acceptance harness 级 interrupt/resume 能力升级为正式前端交互 API
- 触发条件：
  - 前端需要真实显示并回答 clarification
  - 需要把恢复链路正式暴露给调用方
- 前提：
  - 确认 API 形状、SSE 事件语义、UI 交互路径
- 现在不做的原因：
  - 一期收口只要求生命周期能力可运行、可验收
  - 该主题会扩大公开契约，应单独设计

### 2.2 优先级 B：能力扩展

#### 主题 B1：第二个 capability
- 目标：验证主框架不是只为 SQLQuery 特化
- 触发条件：
  - 需要证明 capability 扩展性
- 前提：
  - 明确第二个 capability 的业务价值
  - 明确它不会反向侵入 orchestration 内核
- 现在不做的原因：
  - 一期只冻结并交付首个 capability：SQLQuery 只读 MVP

### 2.3 优先级 C：专题型升级

#### 主题 C1：长期记忆 / 跨任务知识沉淀
- 目标：在会话延续型记忆之外，扩展跨任务知识复用能力
- 前提：
  - 另立专题 PRD
  - 明确与一期会话记忆的边界
- 现在不做的原因：
  - Phase 0 已明确不在一期范围内

#### 主题 C2：LLM 化升级
- 目标：把 SQLQuery 内部生成/总结或主代理任务理解升级为真正 LLM 驱动
- 前提：
  - 单独定义 provider、稳定性、重试、审计策略
  - 先区分 SQLQuery 内部 LLM 化与主代理/通用子代理 LLM 化
- 现在不做的原因：
  - `docs/LLM接入阶段建议.md` 已明确不应混入 Phase 7 收口阶段

## 3. 推荐启动顺序

### 推荐顺序
1. **A1：PostgreSQL 正式化专题**
2. **A2：公开 interrupt / resume 产品面**
3. **B1：第二个 capability**
4. **C1 / C2：长期记忆专题、LLM 化专题**

### 为什么这样排
- A1 / A2 更贴近当前已落地能力，属于“把一期内核变得更可用”
- B1 才是真正验证“通用 capability 扩展”
- C1 / C2 会显著改变系统边界，必须另立专题

## 4. 建议启动 / 暂不启动 / 需先补条件

### 建议启动
- PostgreSQL 正式化专题（若近期目标是从本地闭环走向更正式运行形态）

### 暂不启动
- 长期记忆 / 跨任务知识沉淀
- 主代理任务理解的 LLM 化
- 通用子代理 / worker 型能力的 LLM 化

### 需先补条件再启动
- 第二个 capability
  - 需先明确业务对象与验收价值
- 公开 interrupt / resume API
  - 需先明确前端交互与公开事件契约

## 5. 明确非承诺项

本文件**不是**第二阶段实施承诺，不代表：
- 已经批准 PostgreSQL 改造
- 已经批准长期记忆或 LLM 主题
- 已经开始第二个 capability 开发

它只回答：

> 一期结束后，下一阶段有哪些合理候选主题，它们分别为什么值得做、为什么现在还不做、以及启动前需要补什么条件。
